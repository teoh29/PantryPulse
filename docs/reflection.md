# Personal Reflection — Project_23051105

### 1. OOP Concepts Applied
I applied fundamental Object-Oriented Programming techniques to overcome difficult domain problems in food security management, creating solid and scalable software designs. I created an abstract base class named `InventoryItem` that contained common inventory properties, such as `itemId` and `quantity`, and abstract properties such as `priorityScore()`. On this basis, I then added concrete subclasses, such as `PerishableItem` and `NonPerishableItem`. `PerishableItem` dynamically calculates urgency based on remaining days until expiry using Java's `ChronoUnit.DAYS`, giving highest weight to food expiring within 3 days. In contrast, `NonPerishableItem` prioritizes based on stock shortages against minimum safety levels. The distribution algorithms can work uniformly on a variety of food items without conditional type checks, due to this subtype polymorphic design. In addition, I used parametric polymorphism by creating a generic `Repository[T]` trait with an upper type bound `[T <: Identifiable]`. This provides type-safe `add`, `findById` and `all` operations for inventory items and recipient families, without code duplication. Lastly, I made the domain layer strictly functional by maintaining strict immutability in models. Domain models were constructed as case classes, and all the stock updates were represented by returning completely new object instances via the `withQuantity()` copy method, ensuring zero side-effects and thread-safe data transformations.

### 2. Problems Faced During Development
One of my challenges was untangling ScalaFX wrappers from the underlying JavaFX libraries. Early in the project, my event handlers and table cell factories were throwing type mismatch errors all the time as I was importing Java's `ActionEvent` and `EventHandler` classes instead of taking advantage of the idiomatic ScalaFX `onAction = handle { ... }` closure syntax. Forcing myself to strictly use `scalafx.*` imports required a deep dive into the framework's documentation. The other major paradigm shift was implementing safe file I/O operations without using standard Java `try-catch` blocks. During development of my `FileDataStore` for CSV persistence, I ran into problems with edge cases where there was a fault in parsing a corrupted or empty line that caused an exception and crash the application. To resolve this, I had to learn how to properly wrap risky parsing operations inside monadic `scala.util.Try` and `Either[String, T]` constructs. Finally, this functional approach helped me return failure states back to the `PantryService` that would present an error banner to the user instead of an unhandled stack trace.

### 3. Project Strengths and Weaknesses
The greatest strength of my project is its underlying structural architecture and strict separation of concerns. I spent time upfront creating UML class diagrams and understanding the dependencies, which resulted in a very decoupled system. All UI elements such as `InventoryView` and `DashboardView` are completely isolated from the data persistence layer in the `FileDataStore`. They only communicate via the injected `PantryService`, making the app very modular, testable and simple to add new functionality. Moreover, my project structure guarantees end-to-end reliability in operation. The distribution planner does not only calculate priority matches but enables the coordinators to distribute the plan by single click ("Fulfill & Deduct Stock") which automatically updates the inventory total and saves the changes to disk.

The primary weakness I would address is the simplicity of the `AllocationEngine` algorithm. The current greedy allocation algorithm takes a simple approach of pairing the highest need families with the highest priority stock. It has mathematical caps to prevent households from hoarding but is not sophisticated enough to ensure the maximum nutritional variety and volume of the items they are allocated. Moreover, all the file operations for storing are currently performed synchronously on the main UI thread. This is enough for this scale, but if the data is large, the application window would freeze for a split second during saving, so I would eventually need to add some Scala `Future` constructs for non-blocking, asynchronous data loading.
